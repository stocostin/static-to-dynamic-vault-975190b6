## Goal
Log every Shachavir Assistant conversation to the database so admins can browse chat inquiries from the CMS, alongside contact messages.

## Data model — new migration

Create `public.chat_conversations`:
- `id uuid pk`
- `session_id text not null unique` — random id generated by the widget (kept in `sessionStorage`) so all messages in one visitor session land in one row
- `first_message text` — first user message (preview column)
- `last_message text` — most recent user message
- `message_count int not null default 0`
- `source_page text` — path where the chat started
- `user_agent text`
- `is_read boolean not null default false`
- `is_archived boolean not null default false`
- `created_at`, `updated_at` (with `update_updated_at_column` trigger)

Create `public.chat_messages`:
- `id uuid pk`
- `conversation_id uuid not null references public.chat_conversations(id) on delete cascade`
- `role text not null check (role in ('user','assistant'))`
- `content text not null`
- `created_at timestamptz default now()`
- index on `(conversation_id, created_at)`

RLS + GRANTs (same migration):
- `GRANT INSERT ON ... TO anon, authenticated` for both tables (public widget writes with anon key).
- `GRANT SELECT, UPDATE, DELETE ON ... TO authenticated` (admin views/manages).
- `GRANT ALL ON ... TO service_role`.
- Policies:
  - `INSERT`: `WITH CHECK (true)` for both tables (anyone can log a chat).
  - `SELECT / UPDATE / DELETE`: `USING (has_role(auth.uid(), 'admin'))` on both tables (admins only).
- No `SELECT` grant to anon — widget doesn't need to read back.

## Backend — extend `/api/public/chat`

Update `src/routes/api/public/chat.ts`:
- Accept optional `sessionId` and `sourcePage` in the request body.
- After a successful model reply, use the server publishable Supabase client to:
  1. `upsert` the conversation row on `session_id` (set `last_message`, bump `message_count += 2`, update `source_page` if new, set `user_agent` from request headers on first insert, set `first_message` only when null).
  2. Insert the user message and the assistant reply into `chat_messages`.
- Wrap logging in try/catch — never fail the chat reply because of logging.
- Return `{ reply, sessionId }` so widget can persist the id.

## Notes
- Session-based (not user-based) — visitors are anonymous. `session_id` groups the conversation for the duration of the browser tab.
- No PII beyond what the visitor types is collected. `user_agent` stored for basic triage.
